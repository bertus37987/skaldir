## 2. Fehler und falsche Implementierungen

### E1 — Live-Desktop-Opt-in: zwei unvereinbare Semantiken in einer Ausgabe
- `act_service.py:550` (Bridge-Bericht): „opted in and target-scoped: **only the window**
  '884' may be driven" — während `cu_host_session.py:169` im selben `act check`-Output
  meldet: „FULL DESKTOP: **every window and app** on this session may be driven".
- Docstring `cu_host_session.py:145` beschreibt „switch **and** target", der Code :165
  setzt `allowed = switch alone` (Owner-Rule „ANY opt-in = FULL desktop").
- `cu_host_session.py:166`: `full = bool(allowed)` — `full_desktop` ist dadurch nie
  unterscheidbar; `if allowed and full:` (:167) ist eine tote Bedingung.
- Zusätzlich: `act_service.py:782` schreibt `allow_live_desktop: policy.allow_live_desktop`
  (Policy, hier `false`) neben `live_desktop_allowed: true` (Opt-in) — zwei widersprüchliche
  Werte in derselben Struktur.
- **Auswirkung:** Rechteklärung ist uneindeutig; ein Modell kann die „full desktop"-Meldung
  als Freigabe für alles lesen, obwohl der Bridge-Teil eine Fenster-Kage behauptet.
- **Reparatur:** eine Entscheidung (Owner-Rule „Opt-in = Full Desktop" vs. Target-Cage)
  konsequent durchziehen; `full_desktop` echt berechnen; Docstring an Code anpassen;
  Policy- und Opt-in-Felder einer Quelle zuordnen oder klar benennen.

### E2 — `api_call` ist validierbar, aber unausführbar (Form-Dreieck defekt)
- Validator `act_service.py:1139-1146` verlangt korrekt `payload.url`
  („it is an HTTP call, not a shell command").
- Kein Runner kann diese Form ausführen:
  - `LocalSandboxRunner.act` (`computer_use.py:243-247`): verlangt `action.argv` →
    „argv is missing".
  - `ContainerRunner._default_argv`/`act` (`computer_use.py:711-719`): „no argv for kind".
  - `cu_host_session._full_action_argv` (:1230): nur `if … action.argv`.
- Zusätzlich fahren beide isolierten Runner das Netz ab (bwrap „network namespace off",
  `ContainerRunner` `--network none`, `computer_use.py:8-9,663-664`) — selbst mit
  korrektem `argv` wäre HTTP dort nicht erreichbar (die gemeldeten `curl (6)`-Fehler).
- **Auswirkung:** Jeder `api_call`-Schritt in einer Action-List schlägt fehl; genau der
  im Handoff §15 gemeldete Fall „Launch-/API-Payload widersprüchlich".
- **Reparatur:** entweder einen echten HTTP-Ausführungszweig (hostseitig mit
  Erlaubnisliste) für `payload.url` implementieren, oder `api_call` aus den
  beworbenen Kinds entfernen und die Verträge auf `cli`+argv beschränken.

### E3 — Builder-DI: Agent-Pfad baut `ToolBuilder` ohne Modellclient
- `agent_toolset.py:199` (`skill_expand`) und `:229` (`skill_expand_build`) erzeugen
  `ToolBuilder(runtime, store=…)` **ohne `llm=`**; nur `cli.py:1111` übergibt `llm`.
- `toolbuilder.py:2034` meldet genau diesen Zustand als Fehler
  („client (ToolBuilder(llm=...)) or supply source/tests").
- **Auswirkung:** Der vom Modell ausgelöste Build-Pfad kann nie Code generieren — der
  im Log gemeldete Fehler ist reproduzierbar; nur der CLI-Pfad funktioniert.
- **Reparatur:** denselben konfigurierten Provider-Client per DI in `skill_expand*`
  durchreichen (kein zweiter Provider mit eigener Kostenrechnung).

### E4 — COMPOSE: `end_state="always"` ist der Default und stets wahr
- `compose_service.py:616-617` (`CompositeSpec`), `:742-743` (Parser-Default) und
  `_CONSTANTS` (:302) — „always" ist ein immer wahrer Marker.
- Die Validierung (:1088-1094) akzeptiert ihn explizit als „explicit no-op" statt als
  Warnung; der gemeldete Fall `end_state="always"` (§15) ist damit strukturell begünstigt.
- **Auswirkung:** Ein Composite kann sich trivial „verifizieren"; fachliche Abnahme fehlt.
- **Reparatur:** `always` nur noch mit ausdrücklichem `acknowledge_no_check: true`
  zulassen, sonst Warnung/Problem im Validierungsreport; Beispiele/Defaults ändern.

### E5 — Flow-Dedup meldet „verified" ohne Prüfung
- `agent_toolset.py:379-395`: der 30-s-Dedup gibt `{"ok": True, "status": "verified",
  "skipped": True}` zurück, **ohne** den Endzustand erneut zu prüfen.
- `_flow_key` (:334-343) nutzt im Fallback `id(end_state)` — eine Speicheradresse,
  damit instabil und nicht reproduzierbar.
- **Auswirkung:** Falsche Fertigmeldungen in genau der Risikoklasse, die The Voice/JEV
  verhindern soll (§9.4: „Prozess vorhanden ≠ Fenster sichtbar ≠ richtige Seite").
- **Reparatur:** Dedup-Ergebnis als `skipped_recently` mit Verweis auf die frühere
  Evidence führen, nicht als `verified`; `_flow_key` ohne `id()`.

### E8 — CLI-Darstellung: tote Statuswerte, Mischzustände, unwirksamer Stopp (§11, CLI-06)

- **Auswirkung:** Mehrfachstart über verschiedene Pfade (Subtool vs. `launch`-Action vs.

- **Reparatur:** §5.3-Manager zentral für ACT/Subtools/COMPOSE/Launcher; bevor er steht,
